Traces and Spans in Scala

How Sentry finds a span you never told it about

Brendon Thiede
August 5th, 2026

The question

"Did you ever find out how they are doing span recognition? My mental model of how things works says span detection shouldn't work, but I know it does, so there must be something else going on."

He was right about both halves.

A scope is the bag of stuff on your event

  • tags
  • user
  • breadcrumbs
  • the active span

Fork a scope, set tags, log an error, the error carries the tags.

So where does the scope live?


// io.sentry.DefaultScopesStorage
private static final ThreadLocal<IScopes> currentScopes = new ThreadLocal<>();

A thread-local.

Which is fatal in Scala


fetchPerson(id)          // thread A
  .flatMap(loadOrders)   // thread B
  .map(summarize)        // thread C
  .recover { case e =>   // thread D: who am I? what request is this?
    logger.error("blew up", e)
  }

Every continuation is free to land on a different pool thread.

Prediction: orphan errors

No span. No transaction. An error with no idea which request it came from.

Reality

  • GET /organizations/*/facilities/*/people/*
  • POST /organizations/*/facilities/*/emar/bulkUpdate
  • Errors attached to the right request

Route-templated names, correct linkage, no tracing code anywhere in the app.

The something else


// io.sentry.ScopesStorageFactory
if (Platform.isJvm()
    && loadClass.isClassAvailable(
         "io.sentry.opentelemetry.OtelContextScopesStorage", logger)) {
  // reflectively instantiate it, use it as the IScopesStorage
}
// else: DefaultScopesStorage (the ThreadLocal)

That class ships inside the javaagent jar.

Attach the agent, change the world


// OtelContextScopesStorage
set(scopes) -> Context.current().with(SENTRY_SCOPES_KEY, scopes).makeCurrent()
get()       -> Context.current().get(SENTRY_SCOPES_KEY)
  • Sentry scopes now live in the OpenTelemetry Context
  • Same app code, two different propagation stories
  • Nothing in your code tells you which one you're running

How does a span get into the scope?


// SentryContextWrapper.with(key, value)
result = delegate.with(key, value);
if (isOpentelemetrySpan(key)) {        // is this the OTel *span* key?
  result = forkCurrentScope(result);   // then fork a Sentry scope too
}

Making a span current and forking a Sentry scope are the same operation.

You never opt in. Any instrumentation that starts a span just gave you a scope.

Then capture closes the loop


// SentryClient.applyScope
if (event.getContexts().getTrace() == null) {
  final ISpan span = scope.getSpan();
  if (span != null) {
    event.getContexts().setTrace(span.getSpanContext());       // real span
  } else {
    event.getContexts().setTrace(                              // fallback
      TransactionContext.fromPropagationContext(scope.getPropagationContext()));
  }
}

That is the entirety of "span recognition".

Why the thread hops don't lose it

The agent instruments the things that move context:

  • executors, scala-forkjoin-2.8
  • akkaactor / pekkoactor, akkahttp / pekkohttp
  • netty, reactornetty, rediscala
  • playmvc, playws

Capture Context.current() at submit, re-attach it on the worker thread.

Immutability is the load-bearing part

The task doesn't hold a reference to something mutable that gets popped out from under it. It holds a snapshot that still contains the scope.

So a Future chain started inside a scope keeps the tags, long after the scope was popped on the calling thread.

The comment that was wrong

"block runs on the calling thread and must stay synchronous: the forked scope is thread-local, so async work started inside it would be tagged with nothing."
  • Without the agent (local, tests): exactly right
  • With the agent (prod): the async work is tagged

The rule survives. The reason doesn't, and the reason is what the next person acts on.

Your tests do not exercise your production tracing

Unit tests almost never run with the javaagent.

Every scope assertion you write is an assertion about DefaultScopesStorage, not about the thing that runs in prod.

Three ways to trip

  • The agent jar carries a whole copy of the SDK. It's appended to the system class path, so it wins over your resolved dependency. Pin the versions together or Sentry.init throws.
  • Scope.activeSpan is a WeakReference. Collected wrapper means silent fallback to propagation-context linking. Still looks fine.
  • Sample rate 1.0 finds every naming gap. Our largest bucket was <unlabeled transaction> at over a million a day. Same price as the useful ones.

Confirm it in your own build

  • Log Sentry.class.getProtectionDomain().getCodeSource().getLocation() at boot. Agent jar, or dependency cache?
  • Tag inside a forked scope, start a Future in the same block, log an error from the continuation. Tag present means context is propagating.

Takeaways

  • Sentry's thread-local is not what runs in production
  • Span activation and scope forking are one operation
  • Async survival is the agent's, not your framework's
  • Write down the constraint, not the mechanism you guessed at
